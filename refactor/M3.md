# M3 — Sandbox as the Execution Context

**Core:** Environment (+ State seam). **Release:** R1. **Depends on:**
[M2](M2.md). **Unlocks:** [M4](M4.md), [M5](M5.md). **Size:** L. **Risk:** med.

## Objective

Promote the environment to first-class execution context: `ToolContext.sandbox`,
transactions over **(session, sandbox)**, `WorkspaceSection` dissolved into
`WorkspaceConfig` + provider, and every adapter pointed at `sandbox.root`. After this
milestone there is exactly one environment model.

## Why (first principles)

*Pure core, effects at the edge — and the environment is context, not a
dependency.* Today the filesystem is an optional DI resource reached three
separate ways (`ToolContext.filesystem` at `prompt/tool.py:144-152`,
`FeedbackContext.filesystem` at `feedback.py:194-198`,
`TaskCompletionContext.filesystem` at `task_completion.py:93`), the transaction
machinery scans *every* SINGLETON `Snapshotable` resource per tool call
(`runtime/transactions.py:376-431`), and each adapter independently resolves a
`cwd` (`acp/adapter.py:212 _resolve_cwd`, Codex `config.cwd`, Claude SDK temp
plumbing) that only coincidentally matches WINK's filesystem — and demonstrably
diverges in the remote modes. One `Sandbox` in the context dissolves all of it.

## Stages (each lands green)

1. **`ToolContext.sandbox`** — add the field; `filesystem`/`shell` become
   properties over it; collapse the three parallel `Filesystem | None` shortcuts
   (tool/feedback/task-completion contexts) to one source. Policies and checkers
   (`ReadBeforeWritePolicy` at `policy.py:256-262`, `FileOutputChecker` at
   `task_completion.py:155-169`) read the shared context.
1. **Transactions = (session, sandbox)** — rewrite `runtime/transactions.py`:
   `CompositeSnapshot` = session snapshot + `SnapshotRef | None`; delete the
   generic singleton-`Snapshotable` scan and the `Filesystem`-as-resource binding.
   Fix the adjacent waste: `resources/context.py:257-291` rebuilds
   `_instantiation_order` five times per tool scope.
1. **Dissolve `WorkspaceSection`** — `PromptTemplate` carries
   `workspace: WorkspaceConfig | None`; the workspace preview renders from the *opened*
   sandbox (`filesystem.list`), not copy-time bookkeeping; the refcount/clone
   machinery dies (sharing, if ever needed, is provider-side reuse keyed by the
   fingerprint). Fold `WorkspaceDigestSection` (`contrib/tools/digests.py:123-301`,
   incl. the `summary`-setter inheritance hack) into the same mechanism.
1. **Adapters read `sandbox.root`** — base `evaluate()` flow: read config →
   `sandbox = self.sandbox_provider.open(config)` (provider default:
   `LocalSandboxProvider`) → thread into `ToolContext` → harness
   `cwd = sandbox.root` → `finally: sandbox.close()`. Delete `_resolve_cwd` and
   bespoke temp-dir plumbing in `acp`, `codex_app_server`, `claude_agent_sdk`;
   fold the SDK's isolation knobs — its old `SandboxConfig`, renamed
   `IsolationConfig` — into provider configuration so the environment
   `WorkspaceConfig` is the only user-facing environment input.

## Landed amendment — `AgentRuntime` (lifecycle resolution)

Implementation surfaced a lifecycle tension the stages above left open:
per-`evaluate` open/close lost work across visibility-expansion retries,
broke debug-bundle filesystem capture, and any `evaluate(sandbox=...)`
parameter would let a foreign sandbox reach evaluation. Resolution, landed
with this milestone:

- **`AgentRuntime`** (`adapters/core.py`): a prompt bound to its adapter
  and a live sandbox for one run. The (adapter, prompt, sandbox) triple is
  paired exactly once, inside `ProviderAdapter.runtime(prompt)`; the
  runtime is the only path to `_evaluate`, so a mismatched pairing is
  unrepresentable. `Sandbox.close()` is **lease release** — destroy
  locally, detach/pool-return for future providers ([M4](M4.md)).
- Concrete adapters implement only `_evaluate(..., sandbox)` — no
  lifecycle code; `adapter.evaluate(prompt, session=...)` is one-shot
  sugar over a call-scoped runtime.
- The **adapter keeps its `sandbox_provider`** deliberately: the adapter
  is the authority on which environments its harness can attach to
  (adapter↔provider coherence), while the runtime owns
  adapter↔prompt↔sandbox coherence.
- `AgentLoop` holds one runtime per request, spanning retries, `finalize`,
  and bundle filesystem capture.

The runtime is also where [M4](M4.md)'s harness-launch/attach surface will
live: locally the harness runs on the host with `cwd = sandbox.root`; the
environment-vs-workspace split (the *place* hosting the harness vs the
per-run directory) stays behind the provider until M4 needs it.

## Landed amendment — sandbox everywhere, run state nowhere

A post-review hardening pass tightened three seams the milestone first
landed loosely; later milestones should assume this shape:

- **Render-time workspace preview.** `prompt.render(session=...,
  sandbox=sandbox)` resolves `WorkspacePreviewParams` from the open
  sandbox at render time. Nothing binds run state onto the shared
  `Prompt`; `AgentRuntime.evaluate` no longer mutates the prompt, so one
  `Prompt` instance is safe across concurrent runtimes.
- **Preamble owned by `AgentRuntime.evaluate`.** Budget→tracker
  promotion, effective-deadline resolution, and the fail-fast expiry
  check live in the runtime. `_evaluate` takes no `budget` parameter —
  concrete adapters are now a thin `run_async(self._evaluate_async(...))`
  over harness translation only.
- **Sandbox is non-nullable end to end.** `ToolContext.sandbox`,
  `FeedbackContext.sandbox`, `TaskCompletionContext.sandbox`, the bridge,
  the hook plumbing (`HookContext(sandbox=...)`, required), and
  `runtime/transactions.py` (`create_snapshot`/`restore_snapshot`/
  `tool_transaction`/`PendingToolTracker`) all require a `Sandbox`.
  `CompositeSnapshot.sandbox` is a required `SnapshotRef` (schema v3);
  the `FileOutputChecker` fail-closed-without-filesystem arm and every
  `if sandbox is not None` branch are deleted. The runtime guarantees an
  environment exists (empty `WorkspaceConfig` default), so optionality was
  dead generality.

## Landed amendment — `WorkspaceConfig` / `workspace=` (naming)

The config the template declares was renamed `SandboxConfig` →
`WorkspaceConfig`, and the template field/kwarg `sandbox=` →
`workspace=`. Rationale: the value declares the per-run *workspace*
(mounts, read-only posture, environment seeding) that the Definition core
owns, while the *sandbox* is the live environment lease a provider
materializes — two things sharing one name was the actual confusion
behind "shouldn't this config live on the adapter?". Ownership is
unchanged: templates declare workspaces; adapters (via their provider)
supply environments. [M4](M4.md)'s substrate configuration (where the
harness runs: OS isolation, containers, SSH) belongs on the
adapter/provider side and must **not** be folded back into
`WorkspaceConfig`; until it exists, the substrate-leaning fields
(`egress`, `env`, `setup`) ride on `WorkspaceConfig` as documented on the
class.

## Exit criteria

- `context.filesystem.root == sandbox.root ==` harness `cwd`, asserted per
  adapter; a failing tool rolls back session **and** sandbox via one transaction.
- `grep -rn "WorkspaceSection" src/` is empty; the resource-snapshot scan is gone.
- One `AgentRuntime` spans an `AgentLoop` request: retries reuse the
  sandbox, bundles capture it before release, and no public API accepts a
  sandbox that the runtime did not open.
- `make check` green.

> **Checkpoint:** one environment model, fully local, the adapter as its
> factory and `AgentRuntime` as the bound execution context. Everything
> after this is additive remote capability.
