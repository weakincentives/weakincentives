# M4 — Remote Sandbox

**Core:** Environment. **Release:** R1. **Depends on:** [M1](M1.md)–[M3](M3.md).
**Size:** L. **Risk:** med.

## Objective

A `Sandbox` whose facets live elsewhere: a narrow `SandboxTransport`, remote
implementations of both facets, and a remote provider — validated against two
independent transports: the **ACP adapter running its harness over SSH on a
generic remote box**, and the reference topology, **Codex in a container with a
live-reconfigurable egress/credential proxy sidecar**.

## Why (first principles)

*Local and remote differ only in transport — and this is where the bet pays.*
Because M1 made the filesystem a ~10-method backend and M2 gave exec one surface,
remote is those same primitives over RPC; there is no streaming/text logic to
re-port. The codebase already ships the broken version of this future: with
`CodexAppServerClientConfig.remote_url` (or ACP external `cwd`) the harness's
native tools mutate a remote disk while WINK's filesystem reads a local temp dir.
M4 makes the remote box the *one* environment both halves see. Validating against
**SSH** — a transport WINK neither owns nor can change, present on every box, with
`grep`/`glob` already server-side — is the strongest evidence the waist is right:
if a bare SSH box can be the one environment, the abstraction generalizes, and the
container and (horizon) hosted sandboxes are just two more transports.

## Stages (each lands green)

1. **`SandboxTransport`** — one method per primitive: `stat`, `list`,
   `read_range`, `write`, `glob`, `grep` (**executed server-side** — never
   client-side `rglob` over RPC), `delete`, `mkdir`, `snapshot`, `restore`,
   `exec`, `configure_egress`, `configure_credentials`.
1. **Remote facets** — `RemoteBackend(transport)` implements `FilesystemBackend`
   (transport faults map to the protocol's exception contract; connectivity →
   `RuntimeError`); `RemoteShell(transport)`; `RemoteSandbox` composing them, one
   transport, torn down on `close()`. **Loopback transport** drives a
   `HostBackend`/`LocalShell` in-process: the `FilesystemValidationSuite` and
   `Shell` contract tests run over it — full coverage, no sockets, `FakeClock`.
1. **SSH transport — ACP on a remote box** — `SshSandboxTransport` implements the
   transport over one SSH connection: `exec` runs the command on the box,
   `grep`/`glob` run **server-side** natively (`grep`/`find` over SSH is the
   canonical case), and FS primitives go over `sftp` (range I/O via `dd`/`tee`).
   It validates the *one-environment* invariant on a **generic box, not a
   purpose-built container**: the **ACP adapter runs its harness on the box over
   SSH** — the harness is launched via SSH with its `cwd` a remote path (`acp`
   already supports an external `cwd`); the tool-bridge MCP server is reached back
   through an **SSH reverse tunnel** (`ssh -R`, reusing the bearer-token
   `acp/_mcp_http.py`); and WINK's `RemoteSandbox` over `SshSandboxTransport`
   targets that *same* remote `cwd`. Two channels, one box — the harness's native
   edits and WINK's bridged tools see one filesystem. CI needs only an
   SSH-reachable target (a local `sshd` / `ssh localhost`). Egress/credentials are
   the sidecar's job (next stage); on a bare box egress is the box's own concern,
   or a proxy is launched on it.
1. **Remote provider + reference topology** — `RemoteSandboxProvider` connects
   one concrete transport (the SSH transport above; WebSocket/JSON-RPC with the
   bearer-token pattern already used by Codex WS and `acp/_mcp_http.py`; or
   `podman exec` for a local container). For Codex `remote_url`: **two channels,
   one container** — Codex
   JSON-RPC (threads, native tools) and `SandboxTransport` (WINK facets) both
   terminate at the same root, which is Codex's `thread/start` `cwd`. The
   **proxy sidecar** is the container's outbound chokepoint, doing both jobs:
   *egress* — seeded by `config.egress`, reconfigured **mid-run** via
   `configure_egress` (e.g. open a package registry for a build step, then
   revoke); and *credential injection* — secret material transits the
   authenticated control channel orchestrator → sidecar and lives **only in the
   proxy's memory**, never in the container's env or filesystem. Codex and its
   native tools make credential-less requests that the proxy enriches for
   allowed destinations, so even a fully compromised agent can use but never
   read the secrets, and rotation needs no container restart. WINK adds no
   second sandbox; the container is the perimeter.
1. **(Optional) Funnel mode** — disable harness-native FS/shell tools and expose
   WINK read/write/edit/glob/grep/run tools over the sandbox facets, making
   *every* tool call transactional under (session, sandbox). Off by default;
   the per-adapter choice is declared, not hard-coded.

**Execution-boundary note:** WINK-bridged handlers run in the orchestrator
process (`adapters/_shared/_bridge.py`); their *file* ops reach the container but
their own subprocesses/network egress do not. Side effects belong in
`context.shell` — that is what the funnel mode enforces.

## Exit criteria

- Validation + shell suites green over the loopback transport; fault→exception
  mapping unit-tested.
- **SSH / ACP validation**: with the ACP harness running on an SSH-reachable box,
  a harness-native edit and a WINK `Filesystem.write` observe one filesystem at
  `sandbox.root`, and a WINK `Shell.run` executes on the box — the same
  `FilesystemValidationSuite` passes over `SshSandboxTransport` (CI uses a local
  `sshd`).
- Container integration test: a WINK write and a Codex native edit observe one
  filesystem; `Shell.run` executes in the container; a mid-run
  `configure_egress` change is enforced by the proxy; a request from inside the
  sandbox reaches an allowed host **with credentials attached by the proxy**
  while `Shell.run(["env"])` and a filesystem scan find no secret material
  inside the sandbox.
- Local remains the default; remote is opt-in. `make check` green.
