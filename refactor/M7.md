# M7 — Remote Provider: Codex in a Container

**Depends on:** [M5](M5.md), [M6](M6.md). **Unlocks:** [M8](M8.md).

## Objective

Ship the reference topology: a `RemoteSandboxProvider` plus one concrete
`SandboxTransport`, wired so a `codex app-server` running **inside a remote
container** and WINK's tools share one filesystem.

## Why (first principles)

This is the end the whole refactor exists for: the container is the external
sandbox for Codex *and* its native tools, with isolation and ingress/egress
controls; WINK targets the same environment for its bridged tools. "One
environment, one truth," realized remotely.

## Scope

**New**

- `RemoteSandboxProvider(transport_config)` — `open(spec)` connects a
  `SandboxTransport` to a **co-resident FS/exec daemon in the same container**
  and returns a `RemoteSandbox` whose `root` is the container path used as
  Codex's `thread/start` `cwd`.
- One concrete transport: WebSocket/JSON-RPC (reusing the bearer-token auth
  pattern already in `codex` WS and `acp/_mcp_http.py`), or `podman exec` for a
  local-container variant.

**Wire**

- The Codex adapter, when `remote_url` is set, uses `RemoteSandboxProvider`
  instead of the default local one. Two channels terminate in one container:
  Codex JSON-RPC (threads, native tools) and `SandboxTransport` (WINK facets).

## Reference topology

```
   orchestrator host                         remote container (the sandbox)
   ─────────────────                         ──────────────────────────────
   Codex adapter ──Codex JSON-RPC (ws)────►  codex app-server ─┐
                                                                ├─ one filesystem, one root
   WINK tools  ──SandboxTransport (ws)────►  FS/exec daemon ───┘
                       (RemoteSandbox)        container owns isolation + ingress/egress
```

The Codex protocol exposes no general file/exec access to the client — which is
*why* the second channel exists. WINK adds no second sandbox; the container is the
perimeter.

## Risks & mitigations

- *Execution-boundary surprise.* WINK-bridged handlers still run on the
  orchestrator; their file ops reach the container, but their own
  subprocess/network egress does not. Document this; push side effects through
  `Shell` (and see [M8](M8.md)).
- *Provisioning failures.* `open` must clean up partial state and surface a
  `PromptEvaluationError`.

## Exit criteria

- Integration test against a throwaway container: a WINK `Filesystem.write` and a
  Codex native edit are observed through the same path; a `Shell.run` executes in
  the container.
- Default path stays local; remote is opt-in via adapter config.
- `make check` green.
