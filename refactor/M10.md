# M10 — Harness Capability Negotiation & Graceful Degradation

**Release:** R2. **Depends on:** [M9](M9.md). **Unlocks:** [M11](M11.md).
**Dimensions:** 3, 6, 13. **Priority:** high (mission). **Size:** M.

## Objective

Reconcile what a definition **requires** with what a harness **supports** —
satisfy, degrade gracefully, or fail closed with a precise message — so "runs on
any harness" survives the fact that harnesses genuinely differ.

## Why (first principles)

*Parity is the promise, but harnesses are not identical.* Codex exposes a
`sandbox_mode`; the Claude SDK has bubblewrap/seatbelt isolation; Gemini ACP
reports no token usage and supports HTTP/SSE MCP only; structured-output support
varies. Today these differences leak as silent misbehavior or per-adapter special
cases. Negotiation makes them explicit and safe: a definition states its needs
once; each adapter declares its capabilities once; WINK reconciles.

## Scope

- **`HarnessCapabilities`** (descriptor per adapter): structured output, usage
  reporting, sandbox modes, skills, reasoning effort, MCP transport, cancellation.
- **Definition needs** — `requires=(…)` (hard) and `prefers=(…)` (soft) on the
  `AgentDefinition`/prompt.
- **Negotiation** at bind/evaluate: satisfy → run; unmet *preference* → degrade
  and log; unmet *requirement* → fail closed with a typed error naming the gap.
- Emit the negotiated result in telemetry (and into the `ReplayTrace`, M13).

## Exit criteria

- A definition requiring an unsupported hard capability fails closed with a
  precise message before any model call; soft preferences degrade and are logged
  and observable.
- Each adapter publishes a `HarnessCapabilities`; `make check` green.
